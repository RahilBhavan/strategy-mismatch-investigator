What this connection proves.

A working diagnostic boundary, backed by synthetic records, plus one read-only check of the same method against Strategy’s public demo server. No customer deployment has been exercised.

Implemented here

  • Select two grid-style report references in one synthetic project.
  • Capture metric, prompt/filter, grain, unit and fixed-snapshot context.
  • Compute original and diagnostic totals from underlying records.
  • Return complete-result markers, local instance IDs, bounded retry and cleanup evidence.
  • Export a versioned packet; verify its hash and recompute its arithmetic when reopened.

Documented Strategy concepts

The official report workflow describes report-instance creation, prompt answers, report results and SQL views. SQL-view access requires a specific privilege. The Embedding SDK examples show web integration patterns.

Our adapter operations and fields are locally designed for this POC. They are not captured Strategy responses, certified schema matches or a claim that the same payload can be sent to a live endpoint.

Checked live on Strategy’s public demo

On October 24, 2026, python -m app.live signed in to demo.microstrategy.com with its documented guest login and ran the investigation method in the MicroStrategy Tutorial project. Receipt: verification/live-demo-check.json.

The name of B mentions the category, not the missing Web region. The guest user cannot read B’s filter definition (does not have Read access), so the explanation is numerical: two transient view filters reproduce B exactly. Four transient report instances were created. None of the eight requests wrote to a saved object; the receipt lists them all. Instances were not deleted one by one; they end with the logged-out session.

This proves guest authentication, report-instance creation, transient view filters, totals from real grid payloads, a real read-access refusal (returned as HTTP 500) and session logout on one public build. It does not prove a customer deployment, privileged access, SQL views, prompts, caching, large paging or workload limits. The synthetic app above does not call this server.

Still unverified live

  • Authentication and object permissions on a customer deployment; SQL-view access.
  • Prompt answers, async states, pagination beyond one page and caching.
  • Shared warehouse/cube snapshot semantics and workload limits.
  • Server-side cancellation, instance cleanup and native Library placement.
  • Customer usefulness, competitive uniqueness and commercial demand.

Existing product overlap

Test Center already provides report/baseline comparisons. This POC explores explaining a particular prompt/filter difference through a controlled experiment. A real integration should reuse existing comparison evidence rather than duplicate it.
